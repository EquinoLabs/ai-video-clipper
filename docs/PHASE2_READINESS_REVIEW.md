## 1. Executive Verdict

### Verdict: **READY AFTER SPECIFIC DECISIONS**

The architectural foundation and baseline schemas for Phase 2 are remarkably solid:
- The data contract between transcription output, LLM evaluation, and candidate persistence was pre-designed in TechSpec Section 5.
- Domain models and versioned scoring logic (`calculate_overall_score`, `GOAL_WEIGHTS_V1`, `ScoreBreakdown`) are already implemented and tested in [`backend/app/domain/candidates/scoring.py`](file:///C:/Lakshya/Coding/EquinoLabs/ai-video-clipper/backend/app/domain/candidates/scoring.py).
- Transcript artifacts generated by Phase 1 ([`TranscriptArtifact`](file:///C:/Lakshya/Coding/EquinoLabs/ai-video-clipper/backend/app/domain/transcript/models.py)) provide clean absolute timestamps, word timings, and media duration boundaries.

However, implementation cannot begin safely until **four specific technical and architectural decisions** are resolved:
1. **LLM Provider & Model Selection**: PRD Section 22 and TechSpec Section 17 explicitly mark the LLM provider/model as an **"Open Question"** to be resolved before Phase 2 implementation is locked (e.g., Anthropic Claude 3.5 Sonnet, OpenAI GPT-4o / GPT-4o-mini, or a local/open model via LiteLLM).
2. **Execution Boundary for Phase 2**: Whether Phase 2 should initially be implemented as a **deterministic, local-file CLI command** (mirroring Phase 1's `process_local.py` operating on `transcript.json`) or require the full PostgreSQL/Neon migration and worker infrastructure.
3. **Chunking Budget & Overlap Geometry**: The TechSpec requires chunked transcript analysis with overlapping context, but leaves `TRANSCRIPT_CHUNK_SIZE` and `TRANSCRIPT_CHUNK_OVERLAP_SECONDS` as ellipses (`...`).
4. **Deduplication & Overlap Policy**: The TechSpec requires merging chunk candidate pools and deduplicating near-identical intervals, but the exact overlap metric (e.g., Intersection over Union threshold $\ge 0.70$) and resolution rule (keep higher `overall_score`) must be codified.

## 4. Proposed Candidate Input/Output Contract

### A. Input to LLM Discovery Service
The service consumes the normalized transcript. To prevent context window overflow on 30–60 minute recordings, the transcript is supplied in structured chunks:

```typescript
interface TranscriptChunk {
  chunk_index: number;
  total_chunks: number;
  start_seconds: number;       // Earliest segment start in chunk
  end_seconds: number;         // Latest segment end in chunk
  context_start_seconds: number; // Start including prior overlapping context
  text_payload: string;        // Formatted timestamped transcript lines: "[MM:SS - MM:SS] text"
  segments: TranscriptSegment[];
}
```

Prompt context supplied to LLM:
1. System prompt detailing the editorial goal description and definitions of the 8 scoring dimensions.
2. User instructions or custom goal constraints (if provided).
3. Configured duration constraints (`min_duration_seconds`, `target_duration_seconds`, `max_duration_seconds`).
4. Formatted transcript chunk text with explicit instruction to return timestamps in absolute seconds.

The model must return a JSON payload conforming to:

## 7. Acceptance Criteria & Test Plan

### Acceptance Criteria (from PRD Section 20)
- [ ] A transcript with multiple distinct strong moments produces multiple valid candidates.
- [ ] Insufficient speech material yields fewer candidates (or 0) rather than fabricated or padded moments.
- [ ] Different editorial goals (`humor` vs `education` vs `hook`) produce different scores and rankings for the same transcript.
- [ ] All candidate timestamps map to absolute source positions and satisfy source duration bounds.
- [ ] Candidates lacking necessary context are penalized or rejected.
- [ ] Excessive overlaps and duplicate cuts are resolved automatically.
- [ ] Malformed LLM outputs are safely caught, retried once, or reported with safe diagnostics without crashing.

### Test Plan
1. **Unit Tests (100% Mocked, No API Costs)**:
   - `test_chunking_short_transcript`: Transcript shorter than chunk size produces exactly 1 chunk.
   - `test_chunking_long_transcript_overlap`: Overlap preserves complete segment boundaries and monotonic absolute timestamps.
   - `test_candidate_duration_validation`: Reject candidates $<10\text{s}$ or $>60\text{s}$.
   - `test_evidence_quote_grounding`: Reject candidate when quote does not match transcript text.
   - `test_deduplication_policy`: Candidates with $>50\%$ IoU are suppressed, favoring higher overall score.
   - `test_goal_ranking_differentiation`: Verify `humor` goal prioritizes `goal_specific_impact` while `education` prioritizes `specificity_insight`.
   - `test_malformed_llm_json_recovery`: Test single retry on malformed JSON and safe failure envelope.
2. **Integration Test**:
   - End-to-end run from `outputs/.../transcript.json` to `candidates.json` using a mocked LLM response fixture.
3. **Regression Tests**:
   - Ensure all 38 existing media and transcription tests continue to pass.

## 8. Risks, Dependencies, & Out-of-Scope Work

### Dependencies
- An active API key for the chosen LLM provider (e.g. Anthropic or OpenAI).
- Network access from the backend environment to the provider API.

### Risks & Mitigations
- **Hallucinated Timestamps**: LLMs often approximate start/end seconds. *Mitigation:* The validation layer checks timestamps against segment intervals and snaps or rejects candidates whose evidence quotes do not align.
- **Context Window Limits on Long Transcripts**: A 2-hour interview can exceed 30,000 words. *Mitigation:* Explicit chunking with 45s overlap ensures constant prompt sizes regardless of video length.
- **Provider API Flakiness / Rate Limits**: *Mitigation:* Single retry with backoff; return structured error envelopes; never leave broken candidate files.

### Out-of-Scope for Phase 2 (Guarded Phase Boundaries)
- **NO video rendering or FFmpeg trimming** (Phase 3).
- **NO subtitle generation or ASS/SRT formatting** (Phase 3).
- **NO face detection, crop geometry, or visual sampling** (Phase 5/6).
- **NO Cloudflare R2 uploads or Neon DB migrations** (Deferred until Phase 3/4 service integration).
